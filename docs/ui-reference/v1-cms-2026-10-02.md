# V1 CMS visual and editing reference

Captured October 2, 2026 (America/New_York). **28 actual browser screenshots, not mockups.** This reference records the V1 editing experience used for parity review. It establishes a baseline for future V2 design work; it does not approve V2 or certify every V1 workflow.

## What was already documented, and what is new

SPEC already contained an August V1 walkthrough in prose and many editing requirements. The earlier October comparison primarily established public-site fidelity. A complete curated screenshot walkthrough of the V1 CMS was not found in the inspected earlier evidence locations. This report adds a durable visual reference for the authoring application itself.

V2 acceptance includes visual hierarchy and editing-flow parity with these references. Engineering completion percentages do not establish UI acceptance. Passing backend or browser checks does not establish that the editor looks or feels right.

## Reproduction and scope

Four V1 projects were copied into an isolated sibling workspace: `tsa-cms-admin`, `tsa-humanneedsindex`, `tsa-echelonsymposium`, `tsa-site-host`. Their source was not redesigned or patched. Dependencies were copied so development caches stayed outside the originals. The attached source manifest records SHA-256 hashes for `src`, `public` and `scripts`; originals and copies matched again after the walkthrough.

Firebase Auth, Firestore and Storage ran locally at ports 9099, 8080 and 9199 with project ID `tsa-cms-admin`. Only the disposable emulator administrator was seeded. CMS ran at 5273; HNI at 5173; Echelon at 5175; shared host at 5178. Every Vite app ran in `emulator` mode. No production data was imported and no live site was published. The browser viewport was 1280 × 720. The Mobile/Tablet screenshots show the editor's visitor-preview buttons, not a tablet-sized authoring browser or a phone usability test.

To reproduce on a prepared copy: run `firebase emulators:start --only auth,firestore,storage --project tsa-cms-admin`, then `node scripts/seed-emulator.mjs` in the CMS. Run each project's Vite entry with `--mode emulator --host 127.0.0.1 --port <port> --strictPort`. This capture used Node 24.15.0 and Java 22. The dev servers were launched directly; V1's full gate suite was not run. Keep private environment files out of the copy; use the source `.env.emulator` fixture only.

Empty emulator state matters: page cards start as unsaved drafts, shared header/footer previews use defaults, library usage is zero, and event content uses source starter records. Visible catalogue counts (78 HNI, 90 Echelon) are filtered runtime counts, not the 118-definition V2 migration inventory.

## The experience V2 must preserve

| Reference | Observed V1 strength | V2 acceptance direction |
| --- | --- | --- |
| 01–03 | Navy navigation, calm pale workspace, clear site/page hierarchy; editor gives the canvas the central role. | Design the authoring shell deliberately: readable type, consistent spacing, restrained accents, clear primary actions and useful canvas space. A three-column grid alone is insufficient. |
| 03–06 | Outline and canvas identify the same content; selected section is red, selected field navy; selection reveals the relevant inspector. | Selection must remain obvious after edits, scrolling, insertion and undo. Keep advanced code controls secondary. |
| 04–06 | Actual heading caret, direct canvas typing, synchronized Content field, dirty status and Undo. Rich text exposes a canvas toolbar and a full inspector editor. | Plain-text inline editing is already a V2 requirement. Preserve supported rich-text canvas editing as well, with a safe structured-content round trip; inspector-only rich text is an interim implementation limit, not accepted parity. |
| 07–09 | Typed image/link controls, helpful explanations, swatches, button choices, source-aware section controls. | Match author intentions with contextual controls; show only supported effects and explain site-wide versus section/field scope. |
| 10–12, 18–19 | Real site-themed thumbnails, docked insertion shelf, full preview, categories, recipes and compatibility. | Preserve recognizability and page context. V2 may use efficient static thumbnails, but these must be faithful, current and branded. |
| 13–14 | One responsive page with visitor-size previews. | Keep one content model and responsive design; independently test the V2 authoring shell at tablet width. |
| 15–17 | Separate shared-element and theme workspaces, previews and honest scope explanations. | A page edit must never masquerade as a global change; source branding must survive. |
| 21–25 | Name → look → pages → shared elements → review; real visual choices and a clear draft/public boundary. | Preserve guided creation and meaningful design preview without making authors manage infrastructure. |
| 26–28 | Event content is editable as recognizable records with explicit save/publish actions. | Keep collections understandable and connected to their rendered site. |

These are three independent acceptance dimensions: **CMS authoring appearance and interaction quality**, **V1 website-to-V2 fidelity**, and **V2 preview-to-public agreement**. All must pass. This report does not require freezing every V1 pixel or carrying over its Firebase architecture.

## Walkthrough results and limitations

Verified interactively: opened both site editors; selected typed fields; typed `Human Needs Index — local review` directly into the HNI canvas heading; observed the updated inspector and Unsaved changes; clicked Undo and observed the original content state return. Opened rich-text controls, library categories, a full-size preview, recipes, mobile/tablet modes, shared elements, Design, the creator, all five wizard steps, and an expanded speaker record. The wizard stopped at review; no site was created. The creator's Preview action reported missing Name/Template ID, so successful template creation is not claimed. No drafts or publications were saved during this pass.

Not reverified here: rich-text formatting round-trip, exact caret click position, drag/drop, insertion persistence, uploads, keyboard-only completion, screen readers, permissions, publish/restore, network failure, or the full V1 catalogue. Historical observations in SPEC remain dated evidence, not newly executed tests. This is a reference walkthrough, not an exhaustive regression suite or human pilot. V2 was not rerun for a new matched-state comparison in this pass.

## Defects and cautions to avoid copying

- The Echelon empty-emulator hero displays “Event details coming soon” across the image (26); long fallback text needs a bounded responsive layout.
- The wizard's default preview says button contrast passes at 4.2:1 (22), while the link inspector warns at 3.9:1 and calls for 4.5:1 (08). V2 must apply its resolved-background contrast policy consistently rather than reuse contradictory copy.
- Echelon's top bar wraps several actions at this viewport (26). Preserve access and clarity without crowding the page.
- The docked thumbnails are useful but small; retain a readable full-size preview. Long inspectors need predictable independent scrolling and reachable actions.
- Some source recipe references and production-only workflows are not resolved by this fixture. A visible template list is not proof that every recipe inserts and publishes correctly.

## How to use this reference for future V2 work

Start with 03, 04, 06, 10, 11, 18 and 22. Reproduce the same task and content in V2, at the same browser and visitor-preview sizes; record entry, selected, dirty, recovery and completion states. Compare hierarchy, typography, density, canvas area, selection, labels, feedback, scrolling and brand fidelity. Record every difference as a repair or an explicitly approved improvement. Do not close QA-01 or EDIT-03 based on this V1 report.

Next implementation priorities: (1) matched-state V2 shell/inspector/library review against this reference; (2) restore the missing supported rich-text canvas experience without losing semantic markup; (3) finish cohesive imported fields and branded previews; (4) desktop/tablet keyboard and failure walkthroughs; (5) reviewer visual review and non-technical pilot. The existing stable closure IDs remain authoritative in SPEC and the checklist.
