    Chapter 1 · Start here

    What this CMS is

    A content management system for a family of small websites. Editors click the real page to change it, add designed sections from a shared library, and publish when they are ready. Each site keeps its own look.

    It runs SAWSO and the Echelon sites today, with Better Together 2027 and Human Needs Index kept as reference imports. One installation serves every site: one admin app, one public website app, one background worker and one Postgres database.

    3apps: admin, public site, worker
    6shared packages
    ~80database tables
    548database functions
    6,389unit and database tests
    657browser tests per browser

    Five ideas that explain everything else

    1. A page is a list of sections. A section is a designed block, such as a hero, cards or an FAQ, plus the words and pictures poured into it. Sections come from a library each site shares.
    2. Nothing goes live until it is published. Every save is a private draft. Visitors only ever see published versions.
    3. Nothing is ever overwritten. Every save adds a new version and keeps the old ones. History and restore work because of this.
    4. The database is the security guard. Who can see or change what is enforced inside Postgres, not just hidden on screen. A bug in a screen cannot leak one site's content to another.
    5. One renderer draws both the preview and the live page. What an editor sees in the editor is built by the same code that builds the public page, so they cannot drift apart.

    Chapter 2 · How it works

    The pieces and how they connect

    Editors work in the admin app. Visitors read the public site app. Both talk to one Postgres database, which enforces every permission. A worker handles everything that happens in the background.

    PEOPLEEditors and adminsSign in by email link
    apps/adminAdmin appNext.js. Every screen, editor and workspace. Calls database commands that re-check permission.
    POSTGRESOne databaseEvery site's content, versions, permissions (row-level security), audit log and job queue.
    PEOPLEVisitorsNo sign-in; no JavaScript needed
    apps/sitePublic site appNext.js. Serves every site by web address. Reads only published content.
    apps/workerWorkerBackground jobs: publish-time cache refresh, schedules, thumbnails, media, mail, domains.
    packages/rendererShared rendererImported by both apps. Turns sections into safe HTML, so the editor's preview and the public page are built by the same code. Media files live in a separate file store (Google Cloud Storage when hosted).

    Solid outline: part of this system. Dashed: people. Arrows show who calls whom.

    How a change reaches the public page

    • An editor opens a page.The editor shows the real page, drawn by the shared renderer inside the admin, with a structure tree on the left and settings on the right.
    • They type on the page.About one second after they stop, the change saves as a new private version. If two people edit at once, the second save gets a conflict warning instead of overwriting.
    • They press Publish.The database re-checks that this person may publish this page on this site.
    • Publishing checks run.For example: no main heading, an image without a description, a broken internal link, leftover sample text. Blocking problems need a recorded reason from someone allowed to override.
    • Everything moves in one step.In one database transaction, the page's published pointer moves, the public copy is written, the audit log records it and a background job is queued. Either all of it happens or none of it does.
    • The worker refreshes the cache.The public site serves the new version on the next request, as complete HTML.

    Drafts, versions and history

    Everything an editor can change works the same way: pages, the site look, the menu, the header and footer, site settings, lists and their entries, and section designs. Each has a current record that points to two versions: the draft and the published one.

    • Saving adds a new version and moves the draft pointer.
    • Publishing moves the published pointer.
    • History is just reading older versions. Restore as new draft copies an old version into a new draft; the live page does not change until that draft is published.

    Sections and the library

    A page version is an ordered list of section instances. Each one pins an exact version of its section design, so changing a design in the library never silently changes pages that already use it. Updating a page to a newer design is a deliberate, previewed step.

    Kind of sectionUsed forHow it is built
    StructuredThe core library and native sites such as SAWSO and EchelonA typed tree of headings, text, images, links, buttons, groups and lists. Every field is declared, so every control is typed.
    HTML templateImported and migrated sites that must keep their exact original markupAuthored HTML and CSS with placeholders. Checked by the sanitizer: scripts, event handlers and unsafe links are refused.

    Section styles are scoped to that section, fonts come only from a list of licensed files, and appearance options (spacing, width, alignment, colours from the site look) are a fixed set of choices.

    Releases and scheduling

    Some changes need to go live together, such as a new page and the unpublished pages it links to, or a site's very first publish with its design, header, footer and menu. A release groups them. The CMS rehearses the whole release first, checks every page it would produce, then publishes all of it or none of it.

    Publish later pins the exact reviewed versions to a time. Edits made after review are not included unless they are reviewed too. The worker runs scheduled releases with the same engine as Publish, as the person who scheduled it, and re-checks their permission at that moment.

    Security: who can do what

    The apps never connect as an all-powerful user. Each one has its own database login with only the access it needs:

    Database loginUsed byCanCannot
    cms_authenticated_userAdmin appRead rows for its signed-in person's sites; change data only through named commandsSee another site's data, move a published pointer directly, edit the audit log
    cms_public_rendererPublic siteCall a few read-only functions over published contentRead any draft or editing table
    cms_workerWorkerClaim and deliver queued jobsChange memberships or content outside its commands
    cms_migration_ownerMigrations and backups onlyEverythingBe used by a running app

    People get roles per site, described in Using the CMS. Sign-in is an email link through Supabase when hosted, and a local-only login for development. Public pages contain their content before any script runs, and only reviewed, application-owned scripts are allowed.

    Background work

    The worker reads two job tables in Postgres: an outbox of events written during publishing, and scheduled actions. Jobs are claimed with leases, retried with backoff and set aside if they keep failing. On Google Cloud the worker runs as a private web service that a scheduler calls every minute; it finishes its current job before replying.

    Why it is built this way

    Each choice answers a problem the first version had. See History for the full story.

    ChoiceThe problem it solves
    Pages built on the serverSearch engines and link previews see real content, not an empty page waiting for JavaScript.
    Postgres with row-level securityReal transactions and constraints, and site-to-site isolation enforced in one place instead of a separate rules language.
    One renderer package imported by both appsNo copies of rendering code to keep in sync by hand.
    Editor canvas in the same appNo fragile messaging between two websites, and the editor can be tested automatically.
    Sections stored as versioned dataSection designs can be edited in the CMS without a developer rebuild.
    Job queue inside PostgresScheduling and background work run without a separate paid queue service.
    One standard containerThe whole system can move to another host without a rewrite.

    Everyday tasks

    Short versions below. Each links to the full guide in docs/handbook/.

    Edit a page

    1. Open the site, then Pages, and choose the page.
    2. Click the words or picture you want to change on the page itself, or pick it in the structure tree. Settings for the selected item appear on the right.
    3. Type. Changes save automatically as a private draft. Undo and redo cover every change.
    4. When ready, choose Publish, or send it for review if your role can't publish.

    Guide: editing/pages.md, editing/titles-and-links.md, editing/cards.md, editing/hero-slides.md

    Add a section

    Open the library from the editor and insert a section at a chosen position, by button, keyboard or dragging it onto the page. Site editors and below don't see this; it is for Admins and Super admins. Guide: editing/adding-sections.md

    Publish, schedule and restore

    • Publish shows exactly what will change and any publishing checks. Some checks can be overridden with a recorded reason.
    • Publish later schedules the exact reviewed version for a time. Later edits need their own review.
    • History lists every saved version. Restore as new draft brings one back without touching the live page until you publish.

    Guide: publishing/publish-a-page.md, publishing/schedule-a-page.md, publishing/review-changes.md, publishing/checks.md

    Stories

    Write a story, give it main and secondary tags, and publish or schedule it. The Newsroom order, the story map and Split View are set from the Stories screen. Check for new stories looks for new items from the connected story source. Guide: editing/stories.md, story-tags.md, story-publishing.md, newsroom-order.md, story-world.md, story-split.md

    Media

    Upload photos and files to the site's library, describe them for screen readers, organize them, and set where a picture focuses when it's cropped. Guide: editing/media.md

    Header, menu and footer

    Admins change the logo, header buttons, menu items and their order, and the footer. Changes are drafts until published. Guide: site-setup/header-menu-footer.md

    Site look and fonts

    Admins change colours, buttons and fonts with a live preview. A contrast check warns when text would be hard to read. Guide: site-setup/site-look.md, site-setup/fonts.md

    Echelon chapters

    Each chapter has its own page with shared parts protected. Volunteers edit their chapter and send changes to their division, which approves and publishes. Guide: site-setup/echelon-templates.md, site-setup/chapter-destinations.md

    Contact messages

    Contact form submissions are saved in Settings → Contact messages for site admins. The CMS does not email them, so someone needs to check the inbox.

    Add a person

    Super admins open People. Because email isn't set up, Add person creates their access without sending an invitation; the person then signs in with their own email link once email delivery works. Guide: people/adding-a-person.md

    Coming from Symphony?

    docs/handbook/start-here/coming-from-symphony.md maps Symphony terms to their CMS names, and start-here/glossary.md explains every word the screens use.

    Chapter 5 · Running it

    Setup, tests, deploying and recovery

    For whoever runs the CMS: on a laptop, in testing and on Google Cloud.

    Run it on your computer

    You need Node 24 (the version in .nvmrc), pnpm 11.22.0 and Postgres 16, through Docker or brew install postgresql@16.

    pnpm install
pnpm demo

    The admin opens at http://localhost:3000. Sign in as admin@example.test. The demo loads SAWSO, the Echelon sites, Better Together 2027 and Human Needs Index from local files. Nothing connects to a live website.

    Run the checks

    CommandWhat it checks
    pnpm typecheckStyle lint and TypeScript across every package
    pnpm testUnit tests
    pnpm test:dbDatabase rules against a real, disposable Postgres
    pnpm buildBuilds every app; browser tests refuse a stale build
    pnpm test:e2eBrowser journeys in Chromium and WebKit
    pnpm verifyAll of the above in order
    pnpm format:checkCode formatting

    Run one browser suite at a time, with at most two workers. Never point tests at a database you want to keep.

    Deploy to Google Cloud

    Source comes from the organization's GitHub repository at a reviewed commit. The first installation follows docs/handbook/hosting/bootstrap.md; the project administrator runs the organization commands. In order:

    1. Administrative setup. Project, region, billing and budget alerts, permissions, and an IT-approved way to make the sites public.
    2. Infrastructure. Enable the Google services (Cloud Run, Cloud SQL, Storage, Artifact Registry, Cloud Build, Secret Manager, Firebase Hosting, Scheduler, Monitoring). Create a separate identity for each part; no exported keys.
    3. Database. Postgres 16 on Cloud SQL. Restore the verified content export into an empty database, apply the migrations, compare fingerprints, create the restricted logins.
    4. Media and source. Upload the media and check it against the inventory. Cloud Build builds the image from the committed source.
    5. Runtime. Deploy the Site, Admin and a private Worker on Cloud Run, plus the backup job. Keep scheduling off until operations are accepted.
    6. Routing and sign-in. Firebase Hosting gives each site a review address that forwards to the public site. Add the new Admin /auth/confirm address to Supabase's allowed sign-in callbacks, or sign-in fails.
    7. Operations. Set the minute trigger for the Worker, the backup trigger and health alerts. Check a backup reads back and an alert arrives before turning on scheduling.

    Full steps: deploy/google/README.md. The list of private inputs is in deploy/google/bootstrap.example.json; copy it outside the repository before filling it in.

    What gets handed over privately

    None of this goes in GitHub. The checklist is docs/handbook/hosting/private-release-handoff.md.

    • The cleaned database export and its SHA-256 checksum
    • The database fingerprints file
    • The media folder and its inventory
    • The public asset check file, and the expected page count
    • The Supabase project address and publishable key
    • The Super admin's email

    Ship an update

    1. In a clean checkout: pnpm install --frozen-lockfile, then typecheck, tests and build.
    2. Run the database and browser tests that cover the change.
    3. Review the staged changes, commit and push to the branch for the target environment.
    4. Deploy to staging first, check health and the main routes, then production.

    Separate staging and production with automatic releases are described in docs/handbook/upgrades/automatic-releases.md. Automatic deploys stay off until the deploy identities exist.

    Back up, recover and roll back

    • Wrong content published: use History, or Publish → History → the release → Review recovery. That restores versions as drafts; nothing is lost.
    • Bad code deploy: send traffic back to the previous Cloud Run revision. Keep the previous image digest for this.
    • Lost database: restore the backup into a new, empty database and check it before switching services to it. Never downgrade a migration or restore over live content.
    • Never start a general worker against a restored copy; queued schedules and emails in it are real jobs.

    Detail: docs/handbook/upgrades/backup-recovery.md and docs/operations.md.

    Sign-in and email

    Sign-in uses Supabase email links. The Supabase project should be owned by the organization, not an individual account; Supabase can transfer a project between organizations. Email delivery is not set up: Supabase's built-in sender only reaches members of the Supabase project team, so real editors need a custom email sender (SMTP) configured in Supabase before they can sign in. Options are compared in docs/handbook/hosting/sign-in-options.md.

    Chapter 6 · Changing the code

    Rules for developers and AI agents

    The same rules apply to people and to AI coding agents. Agents should read AGENTS.md in the repository first; this chapter is the plain-language version.

    Never do these

    • Edit an existing migration in packages/schema/migrations/, even a comment. Applied migrations are checksummed. Add a new migration instead.
    • Write around the database commands. Every change goes through the normal draft, review and release commands so permissions, versions and the audit log stay correct.
    • Weaken site isolation or row-level security, or give an app's database login more access to make something work.
    • Bypass the shared renderer or its sanitizer. Section fields cannot add scripts.
    • Commit secrets, database exports, credentials or private manifests.
    • Point tests at a database you want to keep.
    • Weaken a test or raise a timeout to get a pass.

    Conventions

    • Use design tokens and the shared UI components. No raw colours or spacing, and no new rules in globals.css.
    • Keep files under about 800 lines and functions under 300. Split by responsibility, not to make a number smaller.
    • Site-specific behaviour goes behind site settings or capabilities, not checks on a site's name.
    • Comments explain why, only where the code isn't obvious.
    • Check admin screens at 1440 and 1024 pixels wide and public pages at 390.
    • Update the matching handbook guide in the same commit as the feature.

    Before you commit

    1. Run the checks that cover your change: typecheck, unit, database, and the related browser tests.
    2. Format only the files you changed (pnpm format), never the migrations.
    3. Read the staged diff. Make sure nothing private is in it.

    How to approach a change

    1. Find the feature in docs/handbook/maintainers/where-things-live.md.
    2. Read the screen, its server action, the logic in lib/ and the current database command in packages/schema/current/.
    3. Read the existing tests for that feature; they describe the intended behaviour.
    4. Make the change, add or update tests, and update the guide.

    Chapter 8 · History

    How it got here

    The CMS was rebuilt once and refactored twice. Each step kept what worked and fixed what the previous design couldn't.

    JUNE – JULY 2026

    V1: Vue and Firebase

    A Vue admin running in the browser, content in Firestore, and public sites as static files that fetched their content in the visitor's browser. The editor loaded the live site inside a frame and talked to it across two separate websites.

    It got the hard parts right: drafts kept apart from live pages, conflict warnings, database-enforced permissions, review and history, and one renderer for preview and live.

    AUGUST 13 – 17, 2026

    V1.5: the V1 cleanup

    An audit and refactor moved logic out of screens into 16 services and fixed a batch of bugs. The code got much better, but the platform's limits stayed.

    AUGUST 21 – NOVEMBER 6, 2026

    V2: Next.js and Postgres

    A rebuild to remove V1's platform limits. Foundation and security work came first, then on October 25 the editing experience was redone. Released as v2026.11.06.

    NOVEMBER 7 – 8, 2026

    The refactor

    Same architecture, much cleaner code. Large files split by responsibility, the main stylesheet went from 11,796 lines to 39, dead code removed, slow database reads rewritten, and a batch of real bugs fixed. Commit 181fe954.

    Why V1 was rebuilt

    V1 limitHow V2 answers it
    Pages were assembled in the visitor's browser, so search engines and link previews often saw nothingComplete HTML built on the server
    The editor and the site were two websites messaging each other, with timing races, and the editor couldn't be tested automaticallyThe editor canvas lives in the same app and is tested in two browsers
    Firestore had no joins, small batch and document limits, and permissions in a second rules language where bugs hidPostgres with transactions, constraints and row-level security
    Scheduling, media storage and server rendering all needed a paid Firebase planA job queue inside Postgres and a standard container
    Most sections were code, so editing a section meant a developer rebuildSections are versioned data, editable in the CMS

    Can it grow?

    Yes. One database isolates every site, one public app serves every site and the container can run on any host, so adding a site is setup, not new code. Today's limits are hosting settings: one small server instance, a small database tier and two database connections. Raising them needs no code change. Two longer-term limits: all sites share one database, so a very busy site could slow others, and moving a large site to its own database isn't built yet.
